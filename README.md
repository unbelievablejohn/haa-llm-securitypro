## 第 5 天：带认识不确定性判断的问答系统

**核心思路**：不是事后检查答案对错，而是**在生成答案之前**先评估自身的知识不确定性（Epistemic Uncertainty）。

```
用户提问
  ├─ 第一步：模型自评「我是否拥有足够信息回答」→ {confident, confidence(0~100), reason}
  │            confidence < 70  → 直接拒答，绝不生成答案
  └─ 第二步：confidence >= 70  → 才调用模型生成正式回答
```

设计要点：

- **两套独立 system prompt**：判断阶段的提示词明确禁止模型在此阶段答题，否则"先判断再回答"会退化成"先回答再补个分数"
- **`confident` 由程序按阈值计算**，不采信模型自报的布尔值——模型给出分数，与阈值比较的权威性留在程序侧
- **所有失败路径收敛到拒答**：网络异常、JSON 非法、分数越界，一律判为信息不足。失稳方向是"该答的没答"，而非"不该答的瞎答"
- **拒答时输出判断理由**，让用户知道是"无法确认"而不是简单说"不知道"

## 第 5 天（进阶）：三模型独立判断

`day5_multi.py` 把判断阶段从单一模型升级为**三个模型各自独立打分**：

```
用户提问
  ├─ DeepSeek   → confidence_a  ┐
  ├─ 智谱GLM    → confidence_b  ├─ 三个并行调用，互不可见
  └─ 通义千问   → confidence_c  ┘
                    ↓
        聚合（默认取最低分 min）
                    ↓
     < 70 → 拒答（并列出三个模型各自打分）      >= 70 → 生成回答
```

**为什么取最低分**：单个模型的自评有系统性偏差——有的偏自信，有的偏保守。取最低分是保守策略：任一模型没把握就不作答，与"宁可拒答也不要编造"的整体设计一致。聚合方式可改 `AGGREGATION`：`min`（默认）/ `mean` / `majority`。

模型间分歧会同时记录在日志里，可用于观察哪些问题让模型产生分歧。

## 第 5 天（交叉评估）：三个模型轮流当答题者

`day5_cross.py` 让每个模型都当一次答题者，另外两个当裁判：

```
模型A：自评置信度 → 达标才作答 ──┐
                                ├─→ 模型B + 模型C 当裁判，给这份答案打分（0~10）
模型B：自评置信度 → 达标才作答 ──┤
                                │
模型C：自评置信度 → 达标才作答 ──┘
                ↓
        横向汇总：谁更敢答、谁被同伴认可度更高
```

实测结果（2026-10-05）：

| 题目 | 结果 |
|---|---|
| 虚构理论「量子纠缠熵梯度补偿理论」 | **三个模型全部拒答**（DeepSeek 5 / 智谱 0 / 通义 10），跨厂商架构在同一条红线上一致 |
| 847 × 9639 | **暴露严重缺陷**：DeepSeek 答对（8164233），智谱（8193133）与通义（8160533）答错，而 4 次裁判评估**全部给 10/10** |

## 第 5 天（交叉验证改进版）：修复同伴评审的硬伤

`day5_cross.py` 暴露了严重问题：`847 × 9639` 那次，两个算错的答案被 4 次裁判评估全给 10/10。根因有两条，`day5_verify.py` 针对它们各做一处结构性改动：

| 根因 | 改动 |
|---|---|
| 裁判不真的重新计算，只判断答案"像不像对的" | **要求裁判先独立给出自己的答案**，再拿它去比对候选 |
| 每个裁判只看到一份答案，无法借三方矛盾发现问题 | **全部候选同屏**，且顺序打乱、模型名抹去（防止偏袒自己的答案） |
| 依赖模型自觉，程序无从校验 | **程序层冲突检测**：抽取各答案的结论性数值与年份，不一致则强制 `NEEDS_REVIEW`，不依赖裁判是否发现 |

修复前后对比（同一道 `847 × 9639`，真值 8164233）：

| | 修复前（`day5_cross.py`） | 修复后（`day5_verify.py`） |
|---|---|---|
| 裁判是否重新计算 | 否，只看印象 | **三个裁判全部算出 8164233** |
| 错误答案得分 | 10/10 | **0~3/10** |
| 最终裁决 | 错误答案被盖章通过 | **NEEDS_REVIEW，强制人工复核** |

回归验证：

| 案例 | 裁决 |
|---|---|
| `847 × 9639`（三份答案互不相同） | `NEEDS_REVIEW` ✅ |
| 水在标准大气压下的沸点（常识题） | `ACCEPTED` ✅ 无误报 |
| 虚构理论「量子纠缠熵梯度补偿理论」 | `REJECTED` ✅ 三模型一致拒答 |

## ⚠️ API 密钥安全

**源码中不包含任何密钥。** 所有密钥一律通过环境变量传入：

```powershell
$env:DEEPSEEK_API_KEY = "..."
$env:ZHIPU_API_KEY    = "..."
$env:QWEN_API_KEY     = "..."
```

或写入 `.env` 文件（已在 `.gitignore` 中屏蔽，可参考 `.env.example`）。**切勿把密钥硬编码进源码后提交** —— 公开仓库的密钥会被自动扫描并吊销。

`day5.py` 只用 `HAA_API_KEY`；`day5_multi.py` 与 `day5_cross.py` 三个模型需要 `DEEPSEEK_API_KEY` / `ZHIPU_API_KEY` / `QWEN_API_KEY` 全部就位，缺任一个会直接退出并提示。

## 已知问题

- `day4_plus.py` 的「信息完整度」维度恒为 `0.00`：用 `user_query.split()` 按空格切词，中文无空格导致核心词列表恒为空，待修
- `day5` 判断阶段可能给出高置信分，但 `reason` 字段中含错误事实（实测：Ringel–Youngs 定理年份误写为 1967，真值 1968），需补自洽性校验
- `day5_multi.py` 在任一裁判模型调用失败时会保守判为拒答，此时属于"系统故障"而非"模型认为信息不足"，日志中以 `[ERR]` 标记区分
- **`day5_cross.py` 的同伴评审抓不住计算错误**（已实测，见上）：两个算错的答案被 4 次裁判评估全部判为 10/10。原因一是裁判不真的重新计算，二是每个裁判只看到**一份**答案，无法通过三方答案矛盾来发现问题。**该问题已在 `day5_verify.py` 中修复**
- `day5_verify.py` 的程序层冲突检测是启发式规则，仍有局限：只比对数值与年份，对"文字表述互相矛盾但数字相同"的情况无法识别；且当某份答案多提供了背景常数时依赖"共识值"判据来避免误报，规则相对脆弱
