# HAA LLM Security

HAA 计划 · LLM 安全与评测方向的学习实践记录。

从零起步，每天一个可运行的脚本，逐步搭到「带认识不确定性判断的 LLM 问答系统」。

## 第 5 天交付物：`day5.py`

带认识不确定性判断的两步问答系统。

**核心思路**：不是事后检查答案对错，而是**在生成答案之前**先评估自身的知识不确定性（Epistemic Uncertainty）。

```
用户提问
  ├─ 第一步：模型自评「我是否拥有足够信息回答」
  │           输出 {"confident": bool, "confidence": 0~100, "reason": str}
  │           置信分 < 70  → 直接拒答，绝不生成答案
  └─ 第二步：置信分 >= 70  → 才调用模型生成正式回答
```

设计要点：

- **两套独立 system prompt**：判断阶段明确禁止模型作答（否则"先判断再回答"会退化成"先回答再补个分数"）；回答阶段禁止提及内部评估流程
- **`confident` 由程序按阈值计算**，不采信模型自报的布尔值——模型给分数，与阈值比较的权威性留在程序侧
- **所有失败路径收敛到拒答**：网络异常、JSON 非法、分数越界一律判为信息不足。失稳方向是"该答的没答"，而非"不该答的瞎答"
- **拒答时输出判断理由**，让用户知道是"无法确认"而不是简单说"不知道"
- 兼容 OpenAI 接口（智谱 / 千问 / DeepSeek 改 `BASE_URL` 即可切换），`requests` 直连，不接 RAG 与外部检索

### 实测结果

内置两个测试案例，实测输出见 `day5_log.txt`：

| 案例 | 类型 | 自评置信分 | 系统决策 |
|---|---|---|---|
| A：水在标准大气压下的沸点 | 常识题 | **100/100** | 通过 → 生成答案「100 摄氏度」 |
| B：「量子纠缠熵梯度补偿理论」核心机制及 2023 年提出者 | 虚构理论 | **5/100** | **拒答，且未触发第二次模型调用** |

案例 B 是关键：模型自己识别出"并非已知的物理学理论，无法核实其存在及提出者，只能靠猜测或编造"，5 分被拦在生成之前。

## 延伸验证：`day5_verify.py`（非作业要求）

让三个模型互相评估答案，检验"多模型互评能不能替代人工审核"。

```
三个模型各自自评 → 达标才作答
        ↓
程序层冲突检测（确定性，抽取结论性数值与年份比对）
        ↓
每个模型作为裁判，评估全部候选（匿名、顺序打乱）
```

**这个实验有一个明确结论：多模型互评不足以校验精确答案。**

用 `847 × 9639`（真值 8164233）测试，三个模型给出三个不同数字，其中两个是错的（偏差 28900 与 3700）。在最初的实现里，**4 次裁判评估全部给这两个错答案 10/10**——错误被同伴盖章认证。

修复后（裁判须先独立作答 + 全候选同屏 + 程序层冲突检测）：

| | 修复前 | 修复后 |
|---|---|---|
| 裁判是否重新计算 | 否，只判断"像不像对的" | **三个裁判全部独立算出 8164233** |
| 错误答案得分 | 10/10 | **0~3/10** |
| 最终裁决 | 错误被放行 | **`NEEDS_REVIEW`，强制人工复核** |

回归验证（三个案例均符合预期）：

| 案例 | 裁决 |
|---|---|
| `847 × 9639`（三份答案互不相同） | `NEEDS_REVIEW` ✅ |
| 水沸点（常识题） | `ACCEPTED` ✅ 无误报 |
| 虚构理论 | `REJECTED` ✅ 三模型一致拒答 |

实测输出见 `day5_verify_log.txt`。

```powershell
$env:DEEPSEEK_API_KEY = "..."
$env:ZHIPU_API_KEY    = "..."
$env:QWEN_API_KEY     = "..."
.venv\Scripts\python.exe day5_verify.py
```

## 验证过程（`experiments/`）

最终版是结论，`experiments/` 里是**得出结论的过程**——每个脚本都曾发现一个真实缺陷，因此保留而非删除。

验证分三段推进：

| 阶段 | 脚本 | 它发现了什么 |
|---|---|---|
| ① 探测单模型版 | `probe_uncertainty.py` | 用 7 个人工核实过真相的案例打 `day5.py`。覆盖"该拒没拒"与"该答没答"两类风险，发现：**判断阶段可能给出高置信分，但 `reason` 里含错误事实**（实测 Ringel–Youngs 定理年份误写为 1967，真值 1968）——高置信掩盖了错误内容 |
| ② 交叉评估 | `day5_cross.py` | 三个模型轮流当答题者、其余两个当裁判。**暴露了硬伤**：`847 × 9639` 时两个错答案被 4 次裁判全给 10/10。根因是裁判不重新计算、且每人只看到一份答案 |
| ③ 修复验证 | `day5_verify.py` | 针对 ② 的两个根因做结构性改动并复测通过（详见上一节） |

`experiments/day5_cross_log.txt` 是阶段 ② 的**原始失败记录**，故意保留未经修饰——它记录了"多模型互评给错误答案打满分"这一事实，是 ③ 存在的理由。

```powershell
# 复跑阶段①（需 HAA_API_KEY；会真实调用 API）
.venv\Scripts\python.exe experiments\probe_uncertainty.py

# 复跑阶段②（需三个密钥）
.venv\Scripts\python.exe experiments\day5_cross.py
```

> 注：`experiments/` 下的两个脚本通过 `from day5 import ...` 复用主脚本的函数，在其原始位置（项目根目录）运行时导入才生效；若从 `experiments/` 内直接运行，需先把根目录加入 `sys.path` 或把文件移回根目录。

## ⚠️ API 密钥安全

**源码中不包含任何密钥。** 所有密钥一律通过环境变量传入：

```powershell
$env:HAA_API_KEY      = "..."   # day5.py
$env:DEEPSEEK_API_KEY = "..."   # day5_verify.py / day4_plus.py
$env:ZHIPU_API_KEY    = "..."
$env:QWEN_API_KEY     = "..."
```

或写入 `.env` 文件（已在 `.gitignore` 中屏蔽，模板见 `.env.example`）。**切勿把密钥硬编码进源码后提交** —— 公开仓库的密钥会被自动扫描并吊销。

## 已知问题

- `day4_plus.py` 的「信息完整度」维度恒为 `0.00`：用 `user_query.split()` 按空格切词，中文无空格导致核心词列表恒为空，待修
- `day5.py` 判断阶段可能给出高置信分，但 `reason` 字段中含错误事实（实测：Ringel–Youngs 定理年份误写为 1967，真值 1968），需补自洽性校验
- `day5_verify.py` 的程序层冲突检测是启发式规则：只比对数值与年份，对"文字表述互相矛盾但数字相同"的情况无法识别；答案含大量背景数字时，"共识值"判据可能变脆弱
